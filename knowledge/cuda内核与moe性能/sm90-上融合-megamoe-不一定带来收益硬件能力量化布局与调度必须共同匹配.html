根因

MegaMoE 的核心收益来自把 DeepEP dispatch、专家 GEMM、SwiGLU、激活量化和 combine 尽可能融合，并通过共享缓冲区减少中间结果落地与跨卡同步。但这种收益依赖硬件是否能够承载融合后的资源需求。SM90（Hopper）与 SM100（Blackwell）并非只存在指令集差异：SM90 没有 TMEM，WGMMA 累加器主要占用寄存器；FP8 的 scale-factor 计算也缺少专用硬件支持，较多工作由 CUDA core 完成。因此，融合后减少的 kernel launch、访存和同步开销，可能被寄存器压力、流水线停顿、scale 计算以及较差的占用率抵消。

另一个关键因素是比较对象。PR 中的 Hopper baseline 是 DeepEP dispatch + 两次 grouped FP8 GEMM + Triton SwiGLU + DeepEP combine，且 SM90 grouped GEMM 只支持 L2 activation per-128-K scale，而 fused 路径使用 per-64-K scale。两者在数据布局、量化粒度和执行管线方面并不完全等价，因此既不能把 baseline 的输出作为 bitwise correctness oracle，也不能仅凭一个端到端时间判断融合本身的纯收益。部分测试还将 fused kernel 的 GPU 时间与包含通信、combine 和 host 流程的 baseline 时间进行比较，必须明确测量边界。

关键机理

1. 融合会把多个阶段的资源压力叠加到同一个 CTA

MegaMoE kernel 同时负责 token 路由、TMA 搬运、WGMMA 计算、SwiGLU、FP8 量化、scale 写回和跨 rank 通信协同。单独的 grouped GEMM 可以让每个 kernel 专注于矩阵乘，而融合 kernel 必须保存更多中间状态、同步屏障和地址描述符。SM90 上寄存器累加器没有 TMEM 分流，较大的 block_m、block_n 或更多 epilogue warpgroup 会迅速提高寄存器占用，并降低 active warps 或 occupancy。

2. 编译器警告不等于真实寄存器 spill，但仍可能表示性能风险

讨论中的 ptxas 输出同时出现了：

  • 56 bytes stack frame 和 Local memory used；
  • Used 168 registers；
  • wgmma.mma_async instructions are serialized due to wgmma pipeline crossing function boundary；
  • 但最终为 0 bytes spill stores, 0 bytes spill loads。

这说明该版本并没有发生传统意义上的寄存器溢出到 local memory，但存在栈帧、函数边界和 WGMMA pipeline 相关的潜在代价。判断 spill 时应优先看 spill stores/loads、local load/store 指令和实际 kernel profile，不能仅根据 Local memory used 或 stack frame 文本下结论。反过来，即使没有 spill，WGMMA 因函数调用边界被序列化，也可能显著降低吞吐。

3. SM90 的 scale-factor 处理本身可能成为瓶颈

该实现需要处理 FP8 权重、per-128-K 输入 scale，以及 fused L1 epilogue 产生的 per-64-K L2 activation scale。SM90 没有针对这些 scale 操作的硬件加速，SFA/SFB 的读取、转换和计算会消耗 CUDA core、寄存器和共享内存资源。减少 scale 粒度或直接采用不带 scale 的 FP8/FP8 计算可能提升 MFU，但会改变数值语义，必须通过精度和模型级回归验证，不能直接作为无损优化。

4. 调度阈值会造成离散性能悬崖

SM90 路径根据 expected tokens per expert 选择 BLOCK_M、split-N、epilogue warpgroup 数量、expert wave 和 swapAB 等配置。例如讨论中 DSV4 参数在约 448 到 640 tokens 区间出现性能低谷，而 648 tokens 性能突然提升约 50%。这类现象通常不是算力连续变化导致，而是 token 数跨过调度阈值后切换了 block 或 wave 配置，解决方法包括：

  • 打印实际选择的完整 kernel configuration，而不是只打印模型参数；
  • 扫描阈值附近的 token 数，绘制配置和耗时的对应关系；
  • 检查 block padding、每 expert token 分布和最后一个不满 block 的浪费；
  • 将经验阈值从硬编码表提升为可解释的 cost model，或至少保留运行时可覆盖的调参开关。

修复与设计要点

PR 为 SM90 增加了独立的 API、SymmBuffer 布局、权重变换、JIT runtime、heuristics 和测试脚本，主要做法包括：

  • 通过 transform_weights_for_mega_moe_sm90 对 FP8 权重做适合 fused kernel 的 gate/up 交错布局；
  • 对 SM90 使用 FP32 scale，并区分输入 per-128-K 与 L2 激活 per-64-K 的布局；
  • 使用 block_m=64/128、split-N、swapAB、expert wave 和多种 epilogue warpgroup 组合应对 decode 与 prefill；
  • 为调度和实验保留环境变量，例如 DG_SM90_FP8_SWAP_AB、DG_SM90_FP4_PREFILL_E 和 JIT verbose 配置；
  • 用 bench_kineto 抽取 fused kernel 时间，同时用 CUDA event 测量 baseline，并输出 TFLOPS、HBM、NVLink 和 reduction 估算。

讨论中的后续实验还尝试调整计算 warpgroup、修复 swapAB 的 scale pool stride、改变 decode/pre-fill 分界、关闭部分 scale 处理，以及使用 FP8 combine 来减少 NVLink 传输。这些方向说明优化重点已经从“增加融合”转向“降低融合 kernel 的资源压力并改善调度”。

其他测试的边界

另一个 8 卡测试在 hidden=4096、intermediate_hidden=2048 下报告 batch 1 到 1024 约 1.07x 到 1.79x 的 fused 加速，但 batch 4096 和 8192 时分别为 0.995x 和 0.987x，基本没有收益。这进一步说明：

  • decode 场景可以从减少 launch、dispatch/combine 和小矩阵低利用率中获益；
  • 大 token 场景会回到内存带宽、scale 计算、寄存器占用和流水线利用率主导；
  • “融合 kernel 更快”必须按 token 数、每 expert token 分布、EP 规模和测量边界分别报告。

可迁移的工程教训

  1. 先定义公平的基线。 对比时固定量化格式、scale 粒度、通信协议、同步语义和测量范围；如果为了适配现有 grouped GEMM 而改变 scale 粒度，应明确标记为 legacy reference，而不是严格 correctness 或性能基线。

  2. 将 kernel 编译质量纳入性能测试。 JIT kernel 至少应记录 CUDA/NVCC 版本、寄存器数、spill stores/loads、stack frame、local memory 指令和关键 ptxas 警告。不同编译器版本可能改变寄存器分配和 WGMMA 调度，性能结果必须可复现。

  3. 融合不是免费优化。 评估融合收益时，同时检查 occupancy、register pressure、SMEM stages、barrier 数量、TMA wait、WGMMA scoreboard 和 CUDA-core scale 计算。若融合后有效 HBM/SM 利用率下降，拆分成高度优化的 dispatch、GEMM 和 combine 反而可能更快。

  4. 把 decode 和 prefill 当成不同内核问题。 decode 的每 expert token 很少，重点是减少空 tile、同步和固定开销；prefill 的重点是带宽、流水线深度和大 tile 利用率。单套阈值和单一 block 配置很难覆盖两者。

  5. 对阈值附近做连续扫描。 只测 batch=1、512、8192 会隐藏调度断点。应在每个 heuristic threshold 两侧进行细粒度扫描，并记录实际配置、padding 比例、expert wave 数和 kernel 时间。

  6. 硬件差异必须进入设计前提。 SM90 没有 TMEM，不能直接套用 SM100 的寄存器/累加器设计；SM90 的 FP8 scale 也不能假设有 SM100 同等硬件支持。跨架构移植应先建立资源模型，再决定哪些阶段值得融合。

  7. 实验开关要与正式语义隔离。 FP4 activation、FP8 combine、关闭 scale 或修改 swapAB 都可能改变精度和 buffer layout。环境变量适合快速 A/B，但正式 API 应明确 dtype、scale layout、通信格式和兼容性约束，避免 host buffer size 与 kernel view 不一致。

  8. 模型级收益需要和微内核收益分开解释。 kernel 时间变快不代表端到端吞吐一定变快；反之，低延迟路径的收益可能来自减少通信和调度，而非 GEMM MFU 提升。应同时报告 kernel-only、端到端、SLO throughput、精度和 invalid rate。

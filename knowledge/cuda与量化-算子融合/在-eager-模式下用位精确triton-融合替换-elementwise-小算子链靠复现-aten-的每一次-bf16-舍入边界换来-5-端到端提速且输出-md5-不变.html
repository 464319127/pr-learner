背景与根因

扩散模型（Ideogram-4 DiT）在 eager 模式下与 torch.compile 的性能差距，在权重反量化开销被前序 PR（#34305）消除后，剩余的主要来源是大量微小 elementwise kernel 的启动与显存往返——在 TP=2 的 trace 中约占每步 GPU 时间的 15%。具体两条链：

  1. Qwen3 风格 rotate-half RoPE：每层、每个投影（q 和 k 各一次）约 6 个 kernel——四次乘法、两次加/减，外加 qwen3_apply_rotary_pos_emb 内部按切片填充 empty_like 产生的额外写。这些 kernel 全是 memory-bound，算术密度极低，纯粹被 launch overhead 和反复读写同一块显存拖死。
  2. SwiGLU 的 F.silu(w1(x)) * w3(x)：两次遍历整个 FFN 中间张量（silu 一次、乘一次）。注意这里一个关键约束：gate/up 投影是两个独立 GEMM，所以社区常见的 silu_and_mul（要求 gate/up 拼接在同一张量里）用不上——强行用就得先做一次全宽 cat，多出来的这遍读写正好把融合收益吃掉。

为什么可以做到位精确（bit-exact）

这是本 PR 最有迁移价值的部分。两条链都是纯 elementwise，因此可以逐一复刻 aten 的 bf16 舍入边界，从而在数值上完全等价，而不是「误差可接受」：

  • RoPE：eager 计算是 round(round(q1·cos1) − round(q2·sin1))，融合 kernel 写成 round(round(q1·cos1) + round(−q2·sin1))。在 round-to-nearest 下取负是精确操作（只翻符号位），因此两者逐位相等。关键在于不能省掉中间那次 round：aten 的每个独立 op 都会把 fp32 opmath 结果写回 bf16，融合 kernel 必须显式插入 round_bf16_to_fp32 来模拟这个截断点。
  • SwiGLU：silu 在 aten 里是单个 op（fp32 opmath，只 round 一次），乘法再 round 一次。Triton kernel 里 s = round_bf16_to_fp32(a * tl.sigmoid(a))，然后靠 tl.store 到 bf16 输出隐式完成乘法的那一次 round。前提是 tl.sigmoid 下降到与 aten 相同的 fp32 sigmoid 实现——作者在 100 万个随机 bf16 值上用 torch.equal 验证过这一点。

心法：位精确融合的本质是「数出 eager 路径上有几次 dtype 收窄，并在融合 kernel 里精确地重放这些收窄点」。少一次 round 结果就更「准」但不再位精确；多一次则引入额外误差。融合不是自由地在 fp32 里一路算到底。

工程化：默认开启 + 自校验闸门

两个融合都默认挂载，但套在 BitExactFusionGate 后面：

  • 首次调用同时跑融合与 eager，用 torch.equal 在真实张量上比对；
  • 不匹配、抛异常、或形状/dtype/连续性不满足（can_use_fused_* 前置检查）时，永久回退 eager；
  • 验证通过后置 verified 标志，后续调用直接走快路，无额外开销。

这个模式解决了「位精确依赖底层数学库实现，而实现随平台/驱动/Triton 版本变化」的风险：不用靠 CI 矩阵穷举所有硬件，而是让运行时自己在第一步就证明或否证等价性。代价只有一次多余的 eager 计算。前置的 can_use_fused_rope 检查也值得注意——它把 cos/sin 必须是 (B, S, 1, D) 全跨度、bf16、contiguous、同 device、head_dim 偶数等假设全部显式化，而不是在 kernel 里默默做错。

另外两个小细节：kernel 里 tl.program_id(0).to(tl.int64) 的显式提升，避免大张量（FFN 中间维 × batch × seq 很容易超过 2^31）在偏移计算时 int32 溢出；以及通过 register_custom_op 加 fake_impl 注册，保证 kernel 在 torch.compile / meta 追踪下仍可用。

解读：

  • 收益量级与归因自洽：trace 显示 elementwise 占每步 GPU 时间约 15%，实测 denoise 降 4.7–5.1%。融合把 RoPE 的 ~6 kernel 压到 1 个、SwiGLU 的 2 遍压到 1 遍，理论上能拿掉这 15% 中的大部分但非全部（融合后仍需一次读写），实测数字落在合理区间，说明性能归因没有被其它因素污染。
  • H100 相对收益略高于 H200：H200 显存带宽更高，memory-bound 的 elementwise 链本身占比更小，因此消除它的相对收益更低。这符合「带宽越紧、kernel 融合越值钱」的直觉。
  • md5 完全相同是最强的正确性证据：整条几十步的去噪链条上任何一位翻转都会被扩散过程放大并改变最终图像哈希。这比「PSNR/余弦相似度达标」这类阈值式指标强得多——它把「数值回归」这一整类风险从审查清单里彻底移除，因此这类 PR 可以默认开启而无需 flag 保护。
  • Gate 日志零回退：说明两张卡上位精确假设都成立，快路径 100% 生效，表格里的收益不是被部分回退稀释后的结果。
  • 单测层面：融合 RoPE 在多组形状（含 (2,257,16,128)、(1,64,3,64) 这类非规整 seq/head 组合）上与 qwen3_apply_rotary_pos_emb torch.equal；融合 SwiGLU 在 (2,513,3584) 且输入放大 4 倍（覆盖 sigmoid 饱和区）下与 F.silu(a)*b torch.equal；CPU 路径验证回退返回 eager 结果。

数据的一个空白值得注意：作者明确说明此 PR 是对未修改的 main 测量，以隔离本 PR 的效果，与 #34305 的收益是正交的（权重 vs 激活），但没有给出两者叠加后的数字。因此不能直接把两个 PR 的百分比相加。

可迁移教训

  1. 优化 eager 路径之前先做 trace 归因。「eager 比 compile 慢」不是一个可执行的结论；「elementwise 占 15%，其中 RoPE 6 kernel/投影/层」才是。
  2. 纯 elementwise 链是位精确融合的甜区。没有 reduction、没有累加顺序问题、没有 tensor-core 的 fp32 累加差异，只要复现 dtype 收窄点即可。一旦涉及 reduction（如 RMSNorm、softmax）或 GEMM，位精确会变得困难甚至不可能，应改用误差界 + 端到端指标来验收。
  3. 现成 kernel 的接口假设可能让它变负优化。silu_and_mul 要求拼接输入；当 gate/up 是分离 GEMM 时，为迁就接口而加的 cat 会抵消收益。宁可写一个两输入的专用 kernel，也不要为复用而增加一次全宽数据搬运。
  4. 用运行时自校验闸门替代对平台一致性的假设。首次调用比对 + 永久回退，是把「位精确」这种脆弱性质安全地默认开启的通用手法，也适用于任何依赖底层数学库实现细节的快路径。
  5. 把「输出哈希不变」当作优化 PR 的验收标准。对确定性推理管线（固定 seed、固定采样器）而言，md5 相同是零成本、零争议的回归门禁，远优于人工看图或阈值指标。
  6. elementwise kernel 里默认用 int64 算偏移。生成模型的中间张量很容易越过 int32 边界，这类 bug 只在大分辨率/大 batch 下暴露，排查成本极高。
  7. 可复用的 kernel 文件要能被多个模型共享且合并无冲突。本 PR 的 rope_rotate_half_bitexact.py 与 ERNIE 的 #34306 是同一份内容，任意顺序合并都干净——共享 kernel 层与模型层挂载点分离，是并行推进多模型优化的组织前提。

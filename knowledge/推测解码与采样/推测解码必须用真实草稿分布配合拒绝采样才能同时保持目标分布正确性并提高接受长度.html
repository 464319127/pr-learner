根因

原有 EAGLE 流程在生成草稿 token 和目标模型验证时都采用贪心策略：草稿侧直接取 argmax，验证侧也没有使用草稿模型的真实提议概率 q。这虽然省去了完整概率分布的保存和传输，但没有实现经典推测采样的概率校正；特别是在温度较高、分布较平坦时，草稿与目标模型的非最大概率质量被完全忽略，导致后续位置的接受率和平均接受长度偏低。

关键问题不是简单地把接受阈值调宽。阈值式启发规则不能保证最终 token 仍严格服从目标分布 p，而经典拒绝采样可以在使用任意提议分布 q 的同时，通过接受概率和拒绝后的残差采样恢复目标分布。

机理

对于从草稿分布 q 抽出的 token x，经典推测采样按下式接受：

A(x) = min(1, p(x) / q(x))

实现中使用均匀随机数 u，判断 u * q(x) < p(x)，与上述公式等价。若 token 被接受，则继续验证链上的下一个草稿 token；第一次拒绝后停止验证，并从残差分布中抽取替代 token：

r(x) ∝ max(p(x) - q(x), 0)

若整条草稿链都被接受，最后一个 bonus token 直接从下一位置的目标分布 p 中采样。接受步骤与残差补偿共同保证输出边缘分布仍为目标模型分布，而不是草稿模型分布。

草稿侧也必须真正按 q 抽样，而不能继续使用 argmax。本次实现用 torch.multinomial 生成单路径草稿，并保存每一步完整的、经过温度缩放的草稿概率：

q = softmax(draft_logits / temperature)

让草稿侧使用与目标侧一致的温度并非正确性的必要条件，因为拒绝采样对任意合法 q 都成立；它的主要价值是缩小 p 与 q 的差异，从而提升接受率。目标侧仍按实际采样配置执行 temperature、top-k、top-p 和 min-p 归一化，因此验证必须使用运行时真正参与抽样的 p 与 q，不能用原始 logits 或未归一化概率替代。

实现上的关键约束

当前 Triton kernel 只处理 topk=1 的链式推测，不支持多分支树，因此启动时强制 --speculative-eagle-topk=1。它也只允许能产出目标词表完整提议分布的 EAGLE、EAGLE3 和解析为 EAGLE 的 NEXTN，拒绝 STANDALONE、FROZEN_KV_MTP、NGRAM、DFLASH 及多层 EAGLE。

草稿词表必须与目标词表完全一致。若草稿使用 hot-vocab 或缩减词表，需要先通过 draft-to-target 映射把 q scatter 到目标词表空间；否则 p(x)/q(x) 和 max(p-q, 0) 没有共同的 token 坐标，计算结果不成立。本实现选择启动时报错，而不是静默执行错误校正。

拒绝采样与旧的 acceptance threshold 参数语义冲突，因此要求两个阈值都保持 1.0。内核直接使用全局 RNG 生成接受硬币和最终采样硬币，其随机数消费依赖批次形状，无法保证 batch-invariant deterministic inference，所以与确定性推理模式显式互斥。

数据通路与 CUDA Graph 陷阱

拒绝采样需要把每一步完整 q 从草稿 worker 传到验证 kernel，张量形状约为 (batch, num_steps, vocab)。这项状态必须同时覆盖普通执行和系统中的所有批处理生命周期：

  • draft extend 产生第一步 q，多步 draft 持续堆叠后传入 verify input。
  • batch filter、merge、padding、overlap stash/restore 都必须同步处理 draft_probs。
  • CUDA Graph capture 必须预分配静态 full-vocab buffer，replay 前清零并复制当前批次数据。
  • graph capture 还需要构造有效的 SamplingBatchInfo，并在 replay 时更新每个请求的 temperature，否则图内可能使用 capture 阶段的占位温度。
  • idle batch 也要创建形状正确的空概率张量，避免分布式或流水线空转分支破坏接口契约。

这类功能最容易出现的错误不是采样公式本身，而是某个 batch 变换遗漏新张量，造成请求与概率行错位。实现既在启动参数层做能力检查，也在进入 Triton kernel 前再次检查 draft_probs 是否存在及词表维度是否匹配，这种双层校验适合跨 worker、CUDA Graph 和异步调度的数据通路。

完整概率张量也带来明显显存和带宽成本。以 FP32 保存时，额外空间近似为 4 × batch × num_steps × vocab 字节，且 CUDA Graph、overlap buffer 和最终 verify input 可能各自持有副本。大词表、高 batch 或更多推测步数下，应评估峰值显存和复制开销；后续优化可以考虑低精度存储、融合生成与验证，或为缩减词表实现正确的 scatter 映射，但不能只保存已抽中 token 的标量 q(x)，因为拒绝后的残差采样需要完整 p-q。

Triton 内核设计权衡

内核按 batch 一实例串行验证草稿链，在词表维度以 BLOCK_V=4096 分块。拒绝后的最终采样需要两遍扫描词表：第一遍计算残差归一化和，第二遍构造分块 CDF 并定位 token。这避免了额外残差张量和通用采样 kernel 的中间写回，但每次拒绝最多读取两遍完整 p 和 q，性能依赖接受率与词表大小。

目标概率有 num_steps + 1 行，而草稿概率只有 num_steps 行。全部接受时当前位置已经超出草稿概率范围，内核必须保证该分支只读取目标 p，不能投机加载越界的 q。这是 GPU kernel 中容易被分支优化或重构破坏的边界条件。

实现将 norm_sum == 0 时的最终 token 回退为词表最后一个 token，并认为该情况数值上几乎不可能。理论上若 p == q，拒绝概率应为零；但浮点误差、概率归一化差异或 RNG 边界仍可能触发退化路径。任意回退到最后一个 token 会引入分布偏差，更稳健的做法是显式检测极小归一化和并回退到目标分布 p，同时记录诊断指标。

0.905 的分数说明该路径没有出现明显精度崩溃，但单次任务分数和宽松阈值不能证明采样分布严格等价。更有说服力的测试应在小词表上枚举或大量采样，对比 RS 输出频率与目标 p，并覆盖首次拒绝、中间拒绝、全部接受、p(x)=0、q(x)=0、残差和接近零以及不同 temperature/top-p/top-k 配置。

该注册测试在 5090、单卡 H100 和双卡 H100 上连续出现三次失败，之后双卡 H100 重跑通过；评论中没有给出失败根因。最终通过不足以消除随机性、资源配置或多卡时序问题，尤其此功能使用全局 RNG。应固定可控随机种子进行分布测试，把服务启动/资源失败与算法断言失败分开记录，并避免仅靠重跑判定稳定性。

可迁移教训

  1. 推测解码的正确性取决于“生成提议、记录提议概率、接受判定、拒绝补偿”四个环节使用同一套概率语义；只替换其中一个环节通常会产生有偏输出。
  2. q 越接近 p，接受率通常越高，但不要以修改 q 为由省略拒绝后的残差校正。温度对齐是性能优化，p/q 与 max(p-q,0) 才是正确性基础。
  3. 新增跨阶段 GPU 张量时，应系统检查 filter、merge、padding、idle、overlap、CUDA Graph capture/replay 和分布式 worker 边界，不能只修改生产者与消费者。
  4. 对算法能力限制应尽早失败：树形与链式结构、词表映射、确定性要求及旧参数冲突都应在启动阶段明确验证，并在 kernel 边界保留输入形状检查。
  5. 性能报告要区分“相对无推测基线”和“相对现有推测实现”。本例 headline 可达到 +130.8%，但拒绝采样自身的边际吞吐收益最高约为 15.4%。
  6. GPU 概率算法必须为数值退化路径定义无偏或至少可诊断的行为；把极小概率事件直接映射到固定 token，会让罕见浮点问题变成隐蔽的生成偏差。

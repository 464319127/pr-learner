1. 根因：decode 内核被状态读写吃掉带宽

GDN（Gated DeltaNet）的 packed decode 每一步都要把完整循环状态 S [HV, V, K] 从 HBM 读出并写回。在 H20-3e 上 batch ≥ 64 时该内核 70–79% 是 HBM 带宽瓶颈，瓶颈几乎全部来自这份 per-step 的状态 read+write（fp32 状态约 8dn 字节/步）。

注意根因不是 FLOPs 不够快，而是「每步都必须持久化整个状态」这个算法约束。所以正确的优化方向是改变持久化频率，而不是调 block size / warps。

2. 机理：output-only 读出 + 周期性 flush

ReplaySSM（Dao AI Lab）的核心观察：decode 每步真正需要的只有输出 o，完整的新状态可以延迟落盘。做法是每个物理 slot 维护一个长度 L 的环形缓冲，缓存最近 L 步的 (d, k, g)：

  • 当前 token 之前的状态可重建为 S = A·S0 + Σ_j w_j · d_j k_jᵀ，其中总衰减 A = Π α_i、回放衰减 w_j = Π_{i>j} α_i 都可以由缓存的 per-step gate g_j 做一次 cumsum 得到，不需要任何中间状态；
  • 重建按 K 方向分 tile 进行，每个 tile 一算出来就立刻与 q/k 收缩成标量 Sq/Sk，所以 [V,K] 状态从不落 HBM；
  • 只在每 L 步的 flush 上把 S_new = αS + d_cur kᵀ 写回 checkpoint。

结果：per-step 状态流量从 read+write 降到 read-only，约 8dn → 4dn（实测综合约 0.53×），高 batch 下内核理论上限约 1.7×。

一个很实用的可验证性设计：L=1 时环形缓冲恒为空，内核在代数上退化为原 packed decode，因此可以把 packed decode 当作位精确 oracle 来做单测。任何「缓存 + 重放」类优化都值得留这样一个退化点。

3. 最大的性能陷阱：为了过单测而关掉 Tensor Core

重建的计算量是 O(L·K·V)，是 baseline rank-1 更新的 L 倍。这笔额外计算只有跑在 Tensor Core 上（fp32→TF32、bf16→bf16 TC）才能被省下来的带宽掩盖。

PR 中踩到的坑非常典型：为了让单测通过一个过紧的容差，把 tl.dot 强制成 IEEE fp32，Tensor Core 直接失效，内核慢 10–20× —— 从 1.5× 收益变成 15× 回退。

正确做法是反过来：保留 Tensor Core，把测试容差设成「Tensor Core 现实容差」：

路径 重建误差量级 单测容差
fp32 输入（TF32 TC） ~4e-4 atol 1e-4 / rtol 1e-3
bf16 输入（bf16 TC） ~1e-3 atol 1e-3 / rtol 1e-2
GDN L=1（dot 恒为 0） 0 atol 2e-6，近似位精确

误差不累积的论证也值得记住：GDN 每步衰减 α < 1，旧的重建误差会被指数衰减，不会跨 flush 累积到长 decode 上。

可迁移教训：测试容差是被实现的数值路径决定的，不是反过来。当一个单测逼着你改变内核的数值模式时，先问这个改动会不会掉出快路径。

4. 状态游标的三个正确性坑

4.1 write_pos 不能从 seq_len 推导

直觉上 ring 游标 = seq_len % L，但 seq_len 含 prefill 长度，于是某个 slot 的第一个 decode 步就会去读一段全零的「有效」ring。正确做法是把它做成per 物理 slot 的 decode 步计数器：slot 分配时置 0（此刻 prefill 刚把 post-prefill 状态写进 temporal[slot]，正好是合法的 S0 + 空 ring），每个 forward 只推进一次（在 attention metadata 构建处），而不是每层推进一次。

4.2 CUDA Graph 下必须是静态 buffer + device 侧分支

decode forward 只捕获一次并反复 replay，所以 write_pos 不能每步新建 tensor。方案是 per-bs 的静态 buffer 被 graph 按指针捕获，每次 replay 在捕获区之外 in-place 刷新（与 mamba_cache_indices 完全同构）；游标推进也放在同处，并用 not in_capture 保护，避免 warmup/capture 用 dummy slot 污染持久计数器。flush 判定做成 device 侧分支（is_flush = write_pos == L-1），这样一张图能处理批内各行处于 ring 周期任意位置的情况。

4.3 与 radix 前缀缓存的 flush 对齐

radix 会在 seq_lens % mamba_track_interval == 0 时快照 temporal[slot]，而 ReplaySSM 下 temporal[slot] 是滞后的 checkpoint。因此内核必须恰好在这些步 flush。实现上刻意复用了与 schedule_batch.py 完全相同的条件和同一份 post-increment 的 seq_lens_cpu，从根上消除 off-by-one。细节：force_flush 只 OR 进 is_flush，cache_valid 仍用真实 write_pos，保证中途强制 flush 时只读已提交的 ring 条目。

可迁移教训：两处代码要在「同一步」发生的事，最稳的写法是共享同一个输入和同一个判定表达式，而不是各自重算一份等价条件。

5. 评审中挖出的真 bug：finish-donate 的键长/状态长不一致

评审者（kaixih）质疑 copy_from 假设源 slot 已 flush，作者逐个调用点核对后发现 cache_finished_req 确实有洞：

  • L=16，请求 prompt 10 token、输出 20 token，最后一次 flush 在第 26 个 token；
  • 请求结束时 temporal = state@26，ring 里还挂着 27–30 的更新；
  • donate 插入的 radix 节点键是 30 个 token，状态其实是 @26，ring 不会被拷贝；
  • 多轮对话中第二轮前缀正好精确命中该节点，COW 拷进来的状态少了 4 个 token 的更新 → 输出错误。

修复：把 donate 的长度截到最后一个 flush 边界（cache_len -= write_pos）并重置游标，让「键长度 == 状态长度」这个不变量重新成立；未缓存的尾部 token 重新 prefill 即可。同时在 copy_from 上写明不变量，并加一个由 SGLANG_DEBUG_MEMORY_POOL 控制的断言（write_pos[src] == 0），避免在正常路径上引入 device sync。

可迁移教训（很通用）：一旦把「每步都写」改成「延迟写」，所有以「当前状态就是最新状态」为前提的旁路（快照、donate、COW、迁移、PD 分离）都会变成潜在的正确性漏洞。改动前应该枚举所有读该状态的调用点，并把不变量写成文档 + debug 断言，而不是靠记忆。

6. 同一个算法在不同 gate 粒度下收益可能反转（GDN vs KDA）

GDN 与 KDA 是同一套 delta rule，只差 gate 粒度：GDN 是 per-head 标量 α = exp(g)；KDA 是 per-K 通道 S' = S·Diag(a) + d kᵀ。用一个 IS_KDA constexpr 统一，且保证 GDN 路径逐位不变。

但非平凡之处在于 ReplaySSM 会把 gate 累积进重建，所以 per-K 化远不止改一行：

  • g_cache 从 […, L] 变成 […, L, K]（大 K 倍）；
  • 总衰减/回放衰减变成 per-channel cumsum；
  • 回放衰减要折到缓存的 key上（per-K），而不是折到 d 上（标量）；当前 token 的 α 要折进 q/k，不能事后标量乘。

于是带宽收益被抹平：省下的状态写回抵不上 K 倍的 gate 缓存流量 + 每步重折 per-K 衰减的计算。这是「小 metadata」在某个维度上不再小的经典反转案例。

7.5 评审者的 KDA 反测（yyq0210，HV=32, H=16, K=V=128, bf16）

方法上比作者的更严格：让 write_pos 走完整 0→…→L-1→0 周期，所以计时同时包含 ring 重建和 1/L 概率的 flush（amortized），而不是只测最便宜的 non-flush 步。

batch L=8 best / amort L=16 best / amort
16 0.85× / 0.74× 0.85× / 0.78×
64 0.88× / 0.77× 0.88× / 0.82×
256 0.93× / 0.82× 0.93× / 0.87×
  • KDA 在所有 batch 下都比 packed 慢，且 best（最优单步）与 amort（摊销）差 8–11 个百分点；
  • KDA-dense 模型（Kimi-Linear-48B，20 层 KDA）实测 TPOT 稳定回退 ~3.6%，与内核 microbench 方向一致；
  • 相比之下 GDN 在同一 harness 下 batch ≥ 64 摊销后仍有 1.2–1.37×。

作者确认结论一致，处理方式是不下线内核，改为在 flag help 与 dispatch 注释里明确标注 KDA decode 会回退、不推荐（KDA 的 ReplaySSM 收益在投机解码的显存侧，不在 decode），并留待 Blackwell 上重新评估（更高 Tensor Core 吞吐可能翻转 compute/bandwidth 权衡）。

基准方法论教训：周期性开销必须摊销计时。只报「最好的那一步」会系统性高估 1-in-L flush 类优化的收益，本例中高估约 10 个百分点，足以把「回退」讲成「持平」。

8. 其他可复用的工程做法

  • flag-OFF 逐字节等价：关闭时不分配 ring tensor、metadata 字段保持 None、dispatch 自然落回原 packed decode。给高风险内核优化上开关时，「关闭态零差异」应该是硬性验收项。
  • 按可评审切片落地：kernel → 内存池 ring（eager）→ CUDA graph 安全 → 内核 force_flush → radix 对齐 → KDA 泛化，每步一个 commit。这让「哪一步引入回退」可二分定位。
  • 新内存必须进预算账本：mamba_cache_per_req 没有计入 ring 字节，导致 KV pool 被超额分配、默认 mem_fraction_static 下 OOM（临时解法是下调该参数）。任何新增的 per-req 常驻显存都要同步更新容量核算公式，否则表现为「莫名 OOM」而非「显存不够」。
  • 明确划定未覆盖路径并硬失败：PD 分离（HybridMambaDecodeReqToTokenPool 没接收这些参数，flag 会静默 no-op）、extra_buffer ping-pong donation（不走 copy_from，游标不会被重置）都用 ValueError 挡住，而不是任其静默走错路。静默 no-op 比报错危险得多。
  • 保持与上游 diff 友好：内核从 vLLM 的 fused_recurrent_replayssm.py 移植时刻意保留原始数学写法，方便后续同步。

SGLang PR #28695 把 GDN（Gated DeltaNet）推测解码的 target-verify 从「每个 draft token 快照一份完整 [V,K] 状态以便回滚」换成「每 slot 一个环形缓存 + 冻结检查点」。真正值得沉淀的不是这个替换本身，而是它前后两版之间的那个错误：同一套近似数学，放在一次性输出上无害，放在累积状态上会随生成长度爆炸。

一句话机理

输出每步算完就被 sampler 消费掉、丢弃，误差不进入下一步；状态是递推的累加器，任何有偏误差都会被后续每一次 flush 继续携带。设计上必须按「误差是否累积」而不是按「代码是否复用」来划分数值精度策略。

结论：大 batch 下确实被 HBM 卡住，而被卡住的流量正是每个 draft token 的状态快照写入；同时那块快照缓冲（intermediate_ssm，TP1 下 11.48 GB）本身就是 spec-decode 显存的大头。省流量的优化只在 roofline 的带宽侧才有收益，小 batch（6.7%）纯属计算/延迟受限，此时同样的改动不会变快。

根因：开环 d-fold 破坏了递推的收缩性

GDN 递推是 S_t = (I − β_t k_t k_tᵀ) diag(α_t) S_{t-1} + β_t k_t v_tᵀ。逐步扰动增益沿 k 方向是 exp(g)·|1−β| < 1、其他方向 exp(g) < 1——它是收缩映射，注入的误差会自己衰减掉。所以 bf16 递推能跑 32k 输出不崩。

早期版本的 flush 走的是 vLLM 参考实现的做法：把环形缓存里存的 chunked delta d 直接开环折进检查点。问题是 d 是经过 chunked delta-rule 的 (I + A)^{-1} UT 变换算出来的，这个变换最坏情况有 2^(BS−1) 的相消误差放大；再叠加 d 本身的存储量化。这条误差不经过收缩递推，而是直接落在被承诺的状态上，并原封不动喂给之后每一次 flush。误差随生成长度增长，表现为 16k token 之后退化成重复循环（AIME-2024 0.767 vs 递推 0.933，其中一题把同一行复读了 1210 次）。

为什么上游参考实现没暴露

vLLM 参考用的是同一套 fold，只在短输出上验证过。只在短序列上验证过的状态更新，等于没有验证过累积误差。凡是「每 N 步折一次状态」的方案，回归测试必须包含数万 token 的长输出与 loop 检测指标，而不只是 acc。

评审里 @yyq0210 提了个好问题：普通 chunk-prefill 也用同一个 (I+A)^{-1} 并把结果折进 chunk 边界状态，为什么不出问题？答案在于 次数有界：prefill 的 chunk 数被 prompt 长度封顶，有偏误差没机会走远；而 verify 的 flush 在长生成里是无界重复的。同一个数值方法安全与否，取决于它在闭环里被迭代多少次。

修复：闭环 exact fold + 「按位克隆」纪律

graph TD; A[verify step] --> B[输出重建: 检查点 + d/k 历史, chunked I+A逆, tf32]; A --> C[环形写入: rawv/rawk 激活dtype, g/beta fp32]; C --> D[flush: 顺序复放递推更新]; D --> E[fp32 检查点, 与递推基线按位一致]; B --> F[sampler 消费后丢弃]

新的 flush 不再折 d，而是用 gdn_replayssm_exact_fold_kernel 从原始输入顺序复放已承诺窗口。关键在于它是 fused_sigmoid_gating_delta_rule_update_kernel 的按位克隆——不是「数学等价」，是「浮点位等价」：

# 逐字照抄递推 kernel 的算子顺序，不许改写
if USE_QK_L2NORM_IN_KERNEL:
    b_k = b_k / (tl.sqrt(tl.sum(b_k * b_k) + 1e-6))  # 除法形式 + eps 在 sqrt 内
b_h *= tl.exp(b_g)                 # decay
b_v -= tl.sum(b_h * b_k[:, None], 0)  # delta
b_v *= b_beta
b_h += b_k[:, None] * b_v[None, :]    # rank-1 update

为此付出的约束（代码里写成了注释警告，值得抄）：

  • 用除法形式的 L2 norm、eps 放在 sqrt 内——改成倒数乘法就不再按位相同。
  • beta 用显式 1/(1+exp(-x)) 而非 tl.sigmoid。
  • tile 保持 [BK, BV=32]、num_warps=1：归约树的形状由 launch config 决定，改并行度就改了求和顺序。
  • 禁止「顺手优化」成 tl.dot——张量核的累加顺序与标量归约不同。

结果：给定相同输入，折出来的检查点与递推基线 commit 的状态逐位相同，承诺状态的误差不再含任何长度依赖项。chunked 数学只保留在误差无法累积的输出侧。

存原始输入，而不是派生量——「无损」是可以被构造出来的

环形缓存里存 rawv / 前置归一化的 rawk，用激活自身的 dtype（bf16）存。因为它们本来就诞生在 bf16，存进去再读出来是按定义无损的，零量化误差且比 fp32 省一半流量。相反，d 是 fp32 算出来的派生量，存成 16 位必然引入量化。选择存什么，比选择存多宽更重要。

相应地，检查点必须是 fp32（--mamba-ssm-dtype float32，自动设置）：如果检查点是 16 位，每次 flush 都会把刚刚精确折好的状态重新量化一遍，残差重新变成主导项。精确计算的下游必须有精确的存储承接，否则精确性在落盘那一步就被抹掉。

被超越的两个「创可贴」

PR 过程中先后试过 fp16 检查点、以及借用 #26929 的随机舍入（SR）。评审的分析很清楚：SR 只增加方差，而这里没有 SR 能修的偏置；且 Nemotron 那类方案是每步都写状态、误差 O(steps)，ReplaySSM 是 O(flush 次数)，量级本就不同。

四个容易踩的工程坑

1. 用「缓冲区是否存在」当特征开关

老代码把 MambaPool.replayssm_write_pos is not None 当作 --enable-linear-replayssm 的开关。新特征复用了同一块 write_pos 分配，于是 decode 路径误判自己被启用，每步多推进一次游标 → 每步注入一个幻影环条目 → 10k token 后退化成重复。修复是改成判断真正的 flag：

-        return getattr(mamba_pool, "replayssm_write_pos", None) is not None
+        return bool(mamba_pool.enable_linear_replayssm)

可迁移教训：「资源存在性」不是「功能归属」。两个特征共享存储时，所有权必须由显式 flag 表达，并在配置层强制互斥（这里两个 flag 直接报错拒绝共存，因为游标协议不同：按 decode 前向推进 vs 按接受数推进）。同类防御还加在 CUDA graph replay 上——if not in_capture and forward_mode.is_decode_or_idle()，禁止 TARGET_VERIFY 的 replay 推进 decode 游标。

2. Triton：给 tl.dot 的输入 mask 掉整行，会读到未初始化的共享内存

在 padding 行（o_s >= spec_len）上 mask token 维的 load，会让这些行在 MMA 的共享内存暂存区保持未初始化，脏数据泄漏进有效输出列（在 spec_len=2 时复现）。正确做法是把越界 token 索引钳制到合法地址（o_s_safe = tl.where(mask_s, o_s, 0)）、照常整块加载，再靠 q_rnorm/k_rnorm 已为 0 把数值清零。

# 地址钳制而非 mask 掉：staging 被写满，数值上等价
mask_s = o_s < spec_len
o_s_safe = tl.where(mask_s, o_s, 0)
q_tile = tl.load(q + (bos + o_s_safe[:, None]) * stride_q_t + ...,
                 mask=mask_kt[None, :], other=0.0)   # 不 mask token 维

3. 环形缓存的溢出必须在协议层被证明不可能

提议器（n-gram / MTP）无法被要求限制 draft 数量，而拒绝采样器会读取窗口每一个位置的 logits——一个溢出位置就会喂给采样器未初始化的 out，吐出错误 token 并让承诺状态失步。方案是 early-flush 余量：next_is_flush = (new_wp + 2*MAX_SPEC_LEN) > MAX_CACHE_LEN，从而每步都保证 write_pos + spec_len <= ring_len。配套约束：环长必须是 2 的幂（&(L-1) 取模）、L >= 2 * max_draft_tokens，并且在 server_args 与 MambaPool 两处各校验一遍（前者在 draft 数推导之后运行，后者作为兜底）。不变量要在最靠近使用点的地方再断言一次。

4. 「不再需要」的缓冲区必须真的不分配

评审直接指出：只有跳过 intermediate_ssm 的分配，显存收益才会真正兑现。落地方式是把字段改成 Optional[torch.Tensor]、在开关下置 None，并在理论上不可达的递推回退分支放一个响亮的 assert 而不是静默走进 None。同时 conv 的 intermediate window 保留——conv 回滚仍要用它。省显存的改动要顺着「谁消费它」逐条确认，而不是一刀切。

灰度与兼容面（可抄的谨慎清单）

  • 默认关闭、opt-in；GDN + 线性链（topk <= 1）才生效，EAGLE 树验证 / KDA / NPU / CPU 自动回退到原递推 verify（树验证不行的原因是窗口内交互用了严格下三角因果 mask）。
  • 池层面再做一次 GDN 收窄（hybrid_gdn_config is not None），保证其他 mamba 模型带上这个 flag 也逐字节等同于关闭。
  • 已知不兼容显式报错而非静默降级：radix prefix caching（extra_buffer 需要设备侧强制 flush 才能让 temporal 与环一致）、PD 分离。
  • 游标随检查点一起 CPU 往返（get_cpu_copy 返回 3 元组），并同时接受旧的 2 元组；slot 复用/拷贝时把 write_pos/cache_base/is_flush 一起清零——状态机的游标是状态的一部分，任何搬运状态的路径都必须搬运游标。
  • CI 红灯归因：Nemotron 那条 OOM 是 mamba2 模型、不走 GDN，与本 PR 无关。「flag 默认关闭」不等于「与我无关」，但确认无关的正确姿势是指出该路径根本不分配本特征的任何资源。
把系统里的每一份数值按「误差是否进入下一次迭代」分类：一次性消费的量可以大胆用 tf32/低精度换带宽；进入累积回路的量必须走闭环——从原始、无损存储的输入按位复放权威实现，而不是折叠某个近似变换的中间产物。对后者，任何「换舍入模式」「提高存储位宽」的缓解都只是创可贴；判据是残差里有没有长度依赖项，而发现它的唯一手段是长输出 + 重复退化指标的回归测试。
